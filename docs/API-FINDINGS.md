# Live findings (2026-11-03, logged-in probe). No secrets here.

## Auth
- POST authentication/sidebaseMultiplexedLogin/ body is {email, password, recaptcha, vthree, platform}. Without a valid Google reCAPTCHA token the backend returns 400 {"detail":"Problem with reCAPTCHA validation..."}. Pure-HTTP login is IMPOSSIBLE.
- Headless Chrome login fails reCAPTCHA (400). HEADED Chrome via Playwright (headless:false, args ['--disable-blink-features=AutomationControlled'], system Chrome via executablePath/channel 'chrome' works too) on gregmat.com succeeds: click the "Log in"/"Sign in" text on https://gregmat.com/, fill input[type=email] and input[type=password], press Enter; response of .../sidebaseMultiplexedLogin/ is 200 JSON {refresh, access}. Capture BOTH tokens from that network response (better than cookie). Cookie piniaAccess also holds the access token (URL-encoded).
- Bearer access token works on all GET endpoints below. Refresh endpoint authentication/auth/jwt/refresh/ body {refresh} (verify on first run; handle failure by re-running browser login).
- Injecting only the piniaAccess cookie into a fresh browser is NOT enough to be logged in on the frontend (got 401 on /authentication/me/?subdomain=www); irrelevant if we use API directly.
- Required auth flow: GREGMAT_TOKEN / GREGMAT_COOKIE → cached session (~/.gregmat-mcp/session.json with access+refresh, refresh when expired, JWT exp decode) → browser login (Playwright headed, needs a display; on Linux without DISPLAY suggest xvfb-run) with GREGMAT_EMAIL/GREGMAT_PASSWORD, plus a `--login` CLI command that opens a headed browser and lets the user log in manually (Google/Apple sign-in) and captures tokens. Remove the plain-HTTP login attempt (or keep only as a last try that explains the reCAPTCHA error).

## Verified endpoints (base https://gregmat-backend.herokuapp.com, header Authorization: Bearer <access>)
- GET /authentication/me/ → {user:{email, first_name, last_name, is_plus, stripe_subscription_status, current_period_end, subscriptions, per_site_access, ...}}
- GET /ps/stats/ → {quant:603, verbal:315, mini_exams:25}  (TOTAL questions available on site, not user progress)
- GET /ps/question-counts/?super_category=Quant → {sections:{Quant:603,Verbal:315,...}, question_types:{Algebra:162,...}, contexts:{}, tags:{topic_exponents:67,...}} (site totals per topic). super_category is REQUIRED; GRE codes are "Quant" and "Verbal" (NOT GRE-Quant). Verbal returns empty question_types/tags.
- GET /ps/question-tags/ → paginated {count,next,previous,results:[{id,slug,title,type,question_categories:[{code,title}],question_tlcs}]}
- GET /ps/questions/?limit=200&offset=N&super_category=Quant|Verbal (&ordering optional) → paginated {count,next,previous,results:[question]}. Question has: id,title,type (e.g. "Quantitative Comparison"),difficulty,super_category,status ("ToDo"|"Attempted"|"Solved"),acceptance,slug,first_tlc (top-level category e.g. "Arithmetic","Data Analysis","Algebra","Geometry"; for verbal e.g. Text Completion/Sentence Equivalence/Reading Comprehension), tags:[{id,slug,title,type}] (type "topic"/"context"), user_answer_attempts:[{answered_at ISO with offset, correct:bool, first:bool, score, score_denom}], bookmarked, liked, plus_only, has_solution_video. ~918 GRE questions → 5 pages of 200; fetch both categories. This is the main source of solved problems, accuracy, activity dates.
  - Accuracy per topic: use first attempt correctness (first===true) like the site does; group by first_tlc, by type, and by each tag title (type topic).
- GET /ps/quizgroup/gre-mini-exams/ → {title,slug,body,quizzes:[quiz]} (25 GRE Mini Exams)
- GET /ps/quizsupergroup/timed-gre-quant-sections/ and /ps/quizsupergroup/timed-gre-verbal-sections/ → {title,slug,body,quiz_groups:[{title,slug,quizzes:[quiz]}]}
  - quiz: {id,title,slug,minutes,super_category,plus_only,timing_mode,max_score,mean_score,normalized_mean_score,acceptance,dynamic_difficulty,attempts:[] (user's attempts; empty for this user so element shape unknown — treat defensively: look for score/answered_at/created_at/finished_at fields),flags,order_in_group}
  - Quiz sources to aggregate: config list QUIZ_SOURCES = [{kind:'quizgroup',slug:'gre-mini-exams'},{kind:'quizsupergroup',slug:'timed-gre-quant-sections'},{kind:'quizsupergroup',slug:'timed-gre-verbal-sections'}].
- GET /sb/stats/me/ → {pairing|sentencepartselection|blankclassification|sentencefunctionselection: {total_questions,total_attempts,total_first_attempts,total_correct_first_attempts,...}} (skill-building/verbal drills)
- GET /studyplans/?limit=100 → paginated list of plans & modules: {slug,title,plus_only,flags:{planRole:'plan'|'module', planType, parentSlug, moduleIndex}}. Parent plans (planRole plan) have units:[]; their modules are the ones with flags.parentSlug == plan slug, ordered by moduleIndex.
- GET /studyplans/{slug}/ → {title,slug,units:[{id,title,description(html),left_side_title,left_side(html),right_side_title,right_side(html),plus_only,two_sided,done:bool}],flags}. Plan progress = gather all modules of the parent plan, count units done. Detect "plan in use" = plan(s) with any done unit; if none, report "no plan progress recorded" and default to GREGMAT_STUDY_PLAN. Strip HTML for next units (show title + first lines of left_side links text).
- GET /classes/upcoming/ → paginated list (ok).
